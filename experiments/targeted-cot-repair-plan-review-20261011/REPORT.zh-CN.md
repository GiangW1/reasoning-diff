# targeted CoT repair 方案独立审查

审查提交：`9442880f25353c927d1cef4b131c0f29d5c59e94`（`docs: revise targeted CoT repair scoring and request plan-only review`）

审查范围是该提交新增的 `experiments/targeted-cot-repair-plan-20261011/PLAN.zh-CN.md`、`REVIEW_REQUEST.zh-CN.md` 和 `VERIFICATION.json`，并结合 PR10 已上传的自然轨迹审计与独立复核报告。此次只做纸面和静态审查，没有运行模型、smoke test、生成、训练、激活采集、探针或干预，也没有修改实验代码。

## 结论

方案相较上一版已经明显收紧，可以作为执行前设计稿继续修订；当前不建议直接进入正式自然轨迹生成。需要先解决一个阻塞项，并落实几个重要的可实施性约束。修订完成后，先做接口和边界检查，再决定是否进入自然错误队列，不应把本方案当作已有机制验证。

本轮结论是“需修订后进入执行准备”，不是“来源机制已成立”，也不是实验失败。方案自己对小样本、单种子和文本方法的证据边界已有正确限制。

## 保留的优点

1. 方案把主张拆成真实错误定位、已知位置修复、定位与修复组合和后续隐状态机制，明确不以纠正后复发作为继续条件（PLAN §3、§9–18、§202–224）。这忠实承接了 PR10 既有复核：已有轨迹没有确认严格的纠正后同源实际计算复发。
2. B 边界、后缀隔离、假设作用域、局部错误前提和实际采用被分别定义；最终答对不再替代错误传播证据（§49–77、§142–154）。
3. O/C 的强制位置比较与 S/T/Rnd 的策略口径分开，正确位置允许 no-op；无效、截断、未知结果保留在分母并做上界敏感性分析（§107–140、§154）。
4. 488 次请求上限和 S/T、G、F 的 896 token 上限在纸面上自洽。重新处理前缀、生成量和耗时也被列为成本，而不是只比较可见答案 token（§132–140、§168–181）。
5. 方案禁止用人工错误补足自然错误，要求按基础题聚类和固定哈希顺序抽取，并承认 24 题单种子结果只能作为资源决策（§156–200）。

## 阻塞问题

### B1. 根因候选位置与修复接口没有闭合

方案将 Lr、Lc、Lo 和修复器都限制在“四个候选记录”（§95–109），同时把真实根因定义为来源片段、最早原因记录和下游采用位置（§73–77）。但没有明确保证所有可计入主分析的根因都属于这四条记录。

例如，模型可能在第一条指定记录之前形成错误来源解释，或在题面/来源归属句中产生错误，之后四条记录只是错误的消费者。如果此时 Lo 也只能给四条记录，Oracle 不具备修复真实根因的接口；Lr 的“根因集合大小除以四”也不再成立。把这种样本直接算作 O 失败会把接口不可表达误算成修复失败。

**最小修订：** 在执行前冻结候选记录集合与根因标注的映射，并明确二选一：

- 任务协议保证所有主分析根因只能发生在四条候选记录中，验证器逐题检查；或
- 允许记录外根因，但保留在覆盖分母并标为“根因在候选集合外/不可定位”，不进入 O/C 特异性分母，也不把它当作 O 的修复失败；随机基线改按实际候选集合定义。

同时明确来源片段如何映射到可编辑记录，及一个记录不能表达根因时的统一处理。这一项解决前，O/C 和 Lr 的主要比较不可解释。

## 重要问题

### I1. 标注盲法和保存图范围还不够具体

§73–77 要求两位复核者看题面、保存图和截至 B 的上下文，并禁止看原始后缀；但没有定义“保存图”是否含生成后缀的节点、未来数值或答案，也没有明确隐藏 related/noise 条件、任务 ID 和候选分支身份。若保存图含未来结果，或标注者知道某题属于相关干扰条件，就可能从任务设计倒推 E/H/W/A/U。

**建议：** 保存图分成不含模型输出的静态题目依赖图和截至 B 的输出快照；标注包只提供前者、匿名化题目和 B 前缀。条件标签、方法名称、定位预测和分支名称在标注前全部隐藏。固定双人独立标注、分歧保留 U 的规则，并记录逐字段一致率和最终裁决来源。

### I2. B 边界和自由文本解析尚未有可执行验证

§51–57、§158–179 对 B 的定义很严格，但当前 `VERIFICATION.json` 只核对纸面例子、算式和请求预算，并不验证句子切分、thinking 内容、跨段假设作用域或“首次完成四项记录”的解析器。自由生成中出现重复值、未闭合句、表格或内部 thinking 时，若没有固定解析规则，46/48 的可用门槛会变成事后判断。

**建议：** 在正式生成前冻结解析规范和失败类别，使用接口样本验证：完整前缀是否包含全部 thinking、B 是否能机械重建、后缀是否物理隔离、提前出现消费者值时是否必然标为不可用。不能通过改选更晚边界来提高可用率。

### I3. Ls 与 Lt 的优势可能来自提示细化

Ls 的任务提示明确要求核对来源、有效性和假设作用域，Lt 只要求检查任意计算或推理错误（§91–105）。即使输出字段、调用次数和 256 token 上限相同，Ls 的结果更好也可能只是专项提示提供了更强的任务分解，而不是来源身份本身具有额外定位价值。

**建议：** 固定两份提示的输入、输出 schema、位置格式和解析规则，报告输入 token、实际输出量和耗时；结论限定为“来源专项提示相对通用找错提示的定位价值”。如果要宣称来源机制，应在后续另加提示内容匹配或提示消融，不能用本轮文本结果直接证明隐状态来源选择。

### I4. 单种子和小样本门槛只能支持 pilot 决策

方案已承认这一点（§7、§166、§185–200），但执行报告必须严格保留基础题聚类和逐题配对结果。12 条错误轨迹、12 条干净轨迹和单次修复不能给出稳定的机制效应或显著性结论；`ceil(3m/4)`、净胜 2 题等只能决定是否值得扩大，不能被写成方法通过或失败的统计证据。

### I5. 任务生成器的可区分性检查需要落地

§57、§220 要求错误候选不能与其他合法输入/中间结果碰撞，并要求消费者结果可区分，但没有说明自动验证输出。正式生成前应逐题保存参数、依赖图、正确值、错误候选值及 D/I 消费者结果；发现碰撞、相消、零乘子、边界不可用或消费者不敏感时，按预注册规则报覆盖损失，不能临时换题参数。

## 轻微问题

- §170–175 的请求计数是可复算的，但“六个需修复文本的分支”没有逐项列出。建议明确为 O、S、T、Rnd、C、G，避免实现时误把 G 或 O 的请求数重复计算。
- §101 的 Lc 位置匹配使用 Lo 的 token 长度和位置距离；应保存预注册匹配表，防止执行时根据结果换位置。
- 方案已经声明 O/Rnd/C 的 640 token 与 S/T 的 896 token 不是等总算力；报告中应继续把它们称为位置诊断对照，不与端到端策略作直接效率排名。

## 执行顺序建议

1. 先补齐 B1 的候选记录/记录外根因规则和 I1 的匿名盲法。
2. 冻结文本解析、任务生成器验证器、定位提示、修复提示、随机表和预算。
3. 只运行接口样本，验证 B 隔离、候选记录可表达性、替换范围和续写解析；接口失败时停止修订，不进入自然队列。
4. 通过后生成 48 条自然轨迹，先封存 B 和双人标签，再运行定位器和修复分支。
5. 结果只报告逐题配对、根因命中、下游命中、共同消费者 Y、协议失败和成本；满足门槛只表示值得扩大验证。

## 未完成项和边界

本审查没有验证实际模型是否能在 256/128/512 token 上限内稳定输出，也没有验证解析器、任务生成器或修复接口的实现。报告不能替代实验结果；它只判断方案是否具备可检验的执行条件。
